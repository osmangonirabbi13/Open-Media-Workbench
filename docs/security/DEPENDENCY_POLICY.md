# OpenTake — Dependency and Software Supply Chain Policy

**Document Version:** 1.0.0  
**Target Release:** v0.1.0 Beta  
**Status:** Security Baseline Locked  
**Author:** OpenTake Security & Release Engineering Lead  
**Date:** 2026-10-13  

---

## 1. Principles of Dependency Selection

To protect OpenTake from supply-chain compromises, dependency bloat, and unexpected licensing liabilities, every newly proposed crate or npm package must satisfy four criteria:

1. **Demonstrated Necessity (YAGNI):** Standard library solutions (`std::fs`, `std::time`, native DOM APIs) must be exhausted before introducing an external package.
2. **Maintenance Health & Provenance:** Crates must have active maintenance, transparent issue tracking, verifiable GitHub repository provenance, and zero known unpatched security vulnerabilities.
3. **Minimal Transitive Graph:** Packages that introduce dozens of unneeded transitive dependencies are rejected in favor of focused, minimal crates.
4. **License Compatibility:** All direct and transitive dependencies must conform to the project's License Allowlist.

## 2. License Allowlist & Review Matrix

| License Type | Permitted Status | Notes / Conditions |
|---|---|---|
| **MIT / Apache-2.0 / BSD-2 / BSD-3 / ISC** | **ALLOWED** | Standard permissive open-source licenses. Universal compatibility. |
| **MPL-2.0 (Mozilla Public License)** | **ALLOWED with Review** | File-level copyleft; acceptable for isolated components. |
| **GPL-2.0 / GPL-3.0 / AGPL-3.0** | **ALLOWED (GPL aligned)** | Fully compatible with OpenTake's proposed GPL-3.0 licensing model. |
| **Commercial / Proprietary / Subscription** | **STRICTLY FORBIDDEN** | Prohibited in any part of OpenTake. |
| **"Source Available" (SSPL, BSL, Commons Clause)** | **STRICTLY FORBIDDEN** | Violates Open Source Initiative (OSI) guidelines. |

## 3. Vulnerability Auditing & Lockfile Policy

1. **Committed Lockfiles:** Both `Cargo.lock` and `package-lock.json` must be committed to Git. Floating dependency versions during CI builds are strictly forbidden.
2. **Automated Auditing in CI (STEP 25):**
   - Rust: `cargo audit` runs on every pull request to check against the RustSec Advisory Database.
   - Node.js: `npm audit --audit-level=high` runs during frontend CI workflows.
3. **Zero Critical Vulnerabilities:** Any pull request introducing a dependency with a known Critical or High CVSS vulnerability will be blocked by CI release gates.

---

## 4. GitHub Actions & CI Supply Chain Hardening (STEP 27)

1. **Least-Privilege Workflow Tokens:**
   ```yaml
   permissions:
     contents: read
   ```
   Workflows run with read-only permissions by default. Write permissions (`contents: write`) are granted strictly to tagged release publishing jobs.
2. **Untrusted Fork Safety:** Pull requests from external forks are prevented from accessing repository secrets or publishing environments.
3. **Action Pinning:** Third-party GitHub Actions must be pinned to full SHA hashes rather than mutable branch tags.
4. **Binary Artifact Integrity:** Release binaries (AppImage, deb, msi, dmg) generated by GitHub Actions must have cryptographic SHA-256 checksums published alongside the release assets in `SHA256SUMS.txt`.
