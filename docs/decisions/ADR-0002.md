# ADR-0002: Rust Workspace and Module Boundaries

**Status:** PROPOSED  
**Date:** 2026-10-13  
**Authors:** OpenTake Core Architecture Team  
**Deciders:** Lead Systems Architect, OpenTake Core Maintainer  
**Target Release:** v0.1.0 Beta  

---

## 1. Context & Problem Statement
OpenTake combines a native systems core with a Tauri 2 desktop shell. For the initial 30-day beta cycle, we must choose between a minimal two-tier workspace (`crates/opentake-core` + `src-tauri`) or a granular multi-crate architecture (6+ crates). The choice impacts compile times, refactoring speed, testing ergonomics, and cognitive complexity.

## 2. Decision Drivers
- Rapid local development iteration and fast incremental compile times.
- Strict isolation of domain logic from Tauri/UI concepts to guarantee headless testability.
- Avoiding overengineering and package maintenance boilerplate (YAGNI).
- Clean future migration path if modularization is needed post-beta.

## 3. Options Considered
- **Option 1 (Two-Tier Workspace):** A dedicated headless library crate (`crates/opentake-core`) holding all media, EDL, audio DSP, and export domain models, paired with the desktop adapter crate (`src-tauri`).
- **Option 2 (Granular Multi-Crate):** Decomposing the domain into separate crates: `opentake-media`, `opentake-timeline`, `opentake-audio`, `opentake-export`, `opentake-project`.
- **Option 3 (Monolithic Tauri Crate):** Placing all Rust code directly inside `src-tauri/src/`.

## 4. Proposed Decision
Adopt **Option 1 (Two-Tier Workspace: `crates/opentake-core` + `src-tauri`)**.

## 5. Consequences & Tradeoffs
- **Positive:** Enforces strict unidirectional dependency (`src-tauri` -> `opentake-core`). Enables instant headless testing via `cargo test -p opentake-core`. Minimizes Cargo workspace overhead.
- **Negative:** Sub-domains within `opentake-core` share a single crate version.
- **Tradeoff Accepted:** Internal module boundaries (`timeline::`, `audio::`, `export::`) provide sufficient isolation for v0.1.0 without multi-crate packaging friction.

## 6. Risk Assessment & Alternatives Rejected
- Option 2 was rejected as premature optimization that introduces high refactoring costs during beta iteration.
- Option 3 was rejected because coupling domain logic to Tauri structs impedes automated testing.

- Verify clean compilation of workspace manifest in STEP 3 project bootstrap.
