# ADR-0001: Initial Desktop Architecture and Product Scope

**Status:** Proposed  
**Date:** 2026-10-13  
**Authors:** OpenTake Core Architecture Team  
**Deciders:** OpenTake Core Architecture Team, Lead Developer  
**Target Release:** v0.1.0 Beta  

---

## 1. Context & Problem Statement

OpenTake is conceived as a free, open-source, privacy-first desktop application designed for automated and semi-automated spoken-word video editing. The immediate product goal is to deliver an accessible rough-cut tool that eliminates silence, provides timeline review, supports manual editing, and exports watermark-free MP4 videos—all within an estimated 30-day initial development window by a single full-stack engineer utilizing AI assistance.

To achieve this goal without suffering the memory bloat of traditional web wrappers, the instability of rushed native C++ code, or the legal pitfalls of unvetted media dependencies, we must establish a clear, modern architectural foundation.

This Architecture Decision Record (ADR) formally documents the structural choices, options evaluated, rationale, trade-offs, and open questions governing OpenTake v0.1.0 Beta.

## 3. Detailed Architectural Evaluations

### 3.1 Desktop Framework: Tauri 2 vs Electron vs Flutter vs Native GTK/Qt

#### Context
The desktop container hosts the web frontend, manages window lifecycles, and bridges IPC calls to native system APIs and background worker threads.

#### Options Considered
1. **Tauri 2:** Uses the OS's native webview (WebKitGTK on Linux, WebView2 on Windows, WKWebView on macOS) paired with a lightweight native Rust core.
2. **Electron:** Bundles a full Chromium browser instance and Node.js runtime with each application build.
3. **Flutter Desktop:** Compiles Dart to native code with a Skia/Impeller canvas renderer.
4. **Native C++/Rust with GTK 4 or Qt 6:** Direct native GUI application with zero web runtime.

#### Recommendation
**Tauri 2.**

#### Rationale
- **Resource Footprint:** Tauri binaries are typically 10–25 MB with an idle memory footprint of 40–80 MB, compared to Electron's 150+ MB installers and 300–600 MB baseline RAM usage.
- **Security Posture:** Tauri 2 features a fine-grained capability/permission model and native Rust backend isolation, preventing arbitrary remote code execution.
- **Ecosystem Velocity:** Modern web tooling (React, Tailwind, Radix) can be leveraged for fast UI development, while critical system-level tasks (DSP, child processes, filesystem) remain in safe Rust.

#### Trade-offs & Risks
- **Platform Webview Discrepancies:** Linux WebKitGTK, Windows WebView2, and macOS WKWebView have subtle rendering and HTML5 video codec decode differences (especially Linux GStreamer backend dependencies).
- **Mitigation:** Documented preview proxy fallback pipeline in case native video decoding is missing on user Linux installations.

#### Open Questions
- Validation of Tauri 2 Linux packaging (AppImage, deb) under Ubuntu 24.04/26.04 environments in STEP 3.

### 3.2 Native Core Language: Rust vs C++ vs Python vs Node.js

#### Context
The native core is responsible for child process management, audio sample parsing, DSP energy calculations, timeline data structures, and project persistence.

#### Options Considered
1. **Rust:** Memory-safe systems language with zero-cost abstractions and excellent concurrency (`tokio`, `rayon`).
2. **C++:** Industry standard in professional NLEs, but carries manual memory management hazards and segfault risks.
3. **Python:** Rapid prototyping, but packaging self-contained Python binaries cross-platform introduces huge bundle sizes and GIL threading bottlenecks.
4. **Node.js:** JavaScript runtime; high memory usage, poor performance for raw audio PCM DSP loops.

#### Recommendation
**Rust (with Tokio async runtime).**

#### Rationale
- Rust completely eliminates data races, buffer overflows, and null-pointer dereferences in background media tasks.
- Tight native integration with Tauri 2 commands and async event dispatch.
- Outstanding performance for streaming PCM audio processing and JSON serialization (`serde_json`).

#### Trade-offs & Risks
- Strict borrow checker and type system can increase initial development time for novel data models.
- **Mitigation:** Keep data structures simple and avoid complex circular references by using flat interval arrays with UUIDs.

### 3.3 Frontend Framework: React 19 + TypeScript + Vite vs Svelte / Solid / Vue

#### Context
The user interface requires rapid component development, high-frequency timecode updates, timeline canvas rendering, and accessible controls.

#### Options Considered
1. **React 19 + TypeScript + Vite:** Immensely mature component ecosystem, massive developer knowledge base, rich UI libraries (Radix UI, Tailwind CSS, Lucide icons).
2. **Svelte 5:** Compiler-based reactivity with smaller runtime overhead.
3. **SolidJS:** Fine-grained reactive primitives with top-tier DOM benchmarking performance.
4. **Vue 3:** Reactive composition API.

#### Recommendation
**React 19 + TypeScript + Vite.**

#### Rationale
- Rapid development velocity within the 30-day timeline; extensive ecosystem of polished UI primitives (Radix UI / shadcn-style architecture).
- Strict TypeScript typing guarantees synchronized data models between Rust IPC contracts and React state.
- Vite provides instant Hot Module Replacement (HMR) during desktop development.

#### Trade-offs & Risks
- Uncontrolled React re-renders can degrade timeline scrubbing performance.
- **Mitigation:** Isolate high-frequency timeline playhead updates into direct HTML5 Canvas or un-controlled DOM mutations, preventing full-tree React re-renders.

### 3.4 Media Processing Engine: FFmpeg / FFprobe CLI vs libav* C-FFI vs GStreamer

#### Context
OpenTake requires media file probing, audio extraction to PCM, and video splicing/export.

#### Options Considered
1. **FFmpeg / FFprobe as Managed Child Processes:** Invoking standalone, hardened binaries with structured arguments, streaming stdout/stderr over async pipes.
2. **Native C-FFI Bindings to `libavcodec` / `libavformat`:** Direct in-process linkage via Rust crates (e.g., `ffmpeg-next`).
3. **GStreamer Pipeline:** Graph-based multimedia framework.

#### Recommendation
**FFmpeg and FFprobe managed child processes.**

#### Rationale
- **Process Isolation & Crash Immunity:** In-process C-FFI bindings (`libav*`) can crash or segfault the entire desktop application when encountering corrupt video packets. Child processes isolate crashes; an FFmpeg failure is cleanly handled as an error result in Rust.
- **Licensing Safety:** In-process linking triggers strict GPL viral obligations if GPL components (libx264, libx265) are compiled in. Spawning separate processes over CLI / pipe interfaces maintains a clean architectural boundary.
- **Development Speed:** Shell-tested complex filtergraphs can be compiled in Rust and executed directly by FFmpeg without writing low-level frame packet muxing C loops.

#### Trade-offs & Risks
- Spawning child processes incurs a minor startup overhead (10–50 ms per invocation).
- Binary packaging requirement: FFmpeg binaries must either be bundled as Tauri sidecars or validated on the user's host system.

### 3.5 Project Persistence: Versioned JSON vs SQLite

#### Context
Saving project state (media source path, duration, cut ranges, silence settings, UI view state).

#### Options Considered
1. **Versioned JSON (`.opentake`):** Flat human-readable JSON file.
2. **SQLite Database (`.sqlite` / `.db`):** Relational embedded SQL database.
3. **Custom Binary Format (bincode / protobuf):** Packed binary representation.

#### Recommendation
**Versioned JSON (`.opentake`) with atomic write-and-rename.**

#### Rationale
- **Simplicity & Inspectability:** Single-source, single-track projects contain small state sizes (a few kilobytes for hundreds of cuts). JSON is human-readable, easily debugged, and can be inspected in text editors.
- **YAGNI (You Aren't Gonna Need It):** SQLite introduces schema migrations, database connection pooling, and multi-file locking overhead that is unnecessary for small linear project documents.
- SQLite is reserved for future post-beta versions only if multitrack projects or heavy asset caching require it.

#### Trade-offs & Risks
- Potential risk of file corruption if process terminates during write.
- **Mitigation:** Strict atomic persistence pattern: write to `<name>.opentake.tmp`, flush with `fsync`, and atomically rename to `<name>.opentake`.

### 3.6 Processing Topology: Local-First Offline vs Cloud API

#### Context
Determining whether processing occurs on the user's local machine or offloaded to cloud servers.

#### Recommendation
**Strict Local-First Offline Processing.**

#### Rationale
- **Core Product Principle:** Privacy-first and offline-first are foundational tenets. Users must be able to edit and export without an internet connection.
- **Cost & Sustainability:** Zero cloud compute bills allows OpenTake to remain 100% free with no recurring operational server costs.
- **Latency:** Eliminates multi-gigabyte video upload and download wait times.

---

### 3.7 Timeline Architecture: Single-Track EDL vs Multi-Track Compositing

#### Context
Determining the timeline data model for cut representation.

#### Recommendation
**Single-Source, Single-Track Edit Decision List (EDL).**

#### Rationale
- 95% of the target use case (rough-cutting talking-head recordings, podcast silence removal) operates on a single raw video track.
- Multi-track compositing (tracks, layering, blend modes, transitions) increases data model and rendering complexity by an order of magnitude.
- Locking v0.1.0 to single-track ensures rock-solid stability, precise A/V sync, and deterministic export within the 30-day timeline.

---

### 3.8 AI Transcription Strategy: Defer whisper.cpp to P1

#### Context
Commercial tools (Gling) offer speech-to-text transcription to delete text and cut video.

#### Recommendation
**Defer local whisper.cpp speech transcription to Post-Beta (P1).**

#### Rationale
- Bundling Whisper neural models adds 150 MB–500 MB model weight distributions, requires cross-platform BLAS/Vulkan/Metal acceleration compilation, and adds high memory pressure.
- High-quality audio DSP silence detection delivers 80% of creator rough-cut time savings with zero model bloat, near-instant scan speeds, and 100% platform reliability.
- Keeps v0.1.0 Beta tightly focused and deliverable.

---

### 3.9 Extensibility: Defer Plugin Runtime to P2

#### Context
Community requests for custom filter and export plugins.

#### Recommendation
**Defer public plugin runtime to Advanced Future (P2).**

#### Rationale
- Designing a stable, secure public API/ABI for plugins before the core editing engine has stabilized leads to broken APIs and security vulnerabilities.
- Core engine stability and user experience must be perfected first.

---

## 4. Consequences & Impact Summary

### Positive Consequences
- Lightweight, fast-launching desktop application (< 100 MB RAM idle).
- Zero cloud infrastructure costs; 100% user privacy guaranteed.
- Deterministic, verifiable A/V sync on export.
- Clean development path enabling delivery within ~30 days.

### Negative Consequences / Accepted Limitations
- Re-encoding is required for final export (takes longer than stream copy, but guarantees frame accuracy).
- No multitrack B-roll or text-based word deletion in the initial v0.1.0 Beta.
- Requires platform validation of host FFmpeg binaries across different operating systems.
