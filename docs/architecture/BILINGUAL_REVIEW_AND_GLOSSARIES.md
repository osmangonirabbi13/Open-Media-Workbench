# STEP 23 — Bilingual Subtitle Review, Glossary Management & Translation Memory Architecture

## Executive Summary

STEP 23 establishes an offline human-in-the-loop translation review and terminology governance domain for localized media in Open Media Workbench. Building upon STEP 22's offline translation engine and STEP 21's styling and burn-in export pipeline, this architecture enables reviewers to inspect side-by-side bilingual subtitles, preserve brand names deterministically, enforce preferred terminology, query exact translation memory suggestions, and manage review state persistence directly within canonical `.omwsub` subtitle projects.

---

## 1. Domain Architecture & Canonical Model

### 1.1 Data Schema

Located in `crates/opentake-core/src/ai/translation/review/`:

- **`TranslationReviewDocument`**:
  - `schema_version`: Document schema version (`1`).
  - `review_id`: Unique identifier (`rev-<uuid>`).
  - `document_id`: Associated `.omwsub` project ID.
  - `source_track_id`, `target_track_id`: Stable SubtitleTrack references.
  - `source_language`, `target_language`: Normalized BCP-47 codes (e.g. `en`, `es`, `bn`).
  - `source_revision`, `target_revision`: Track revision fingerprints.
  - `entries`: Ordered sequence of `TranslationReviewEntry` instances.
  - `referenced_glossary_ids`: Glossaries active during the review session.
  - `created_at_epoch_ms`, `updated_at_epoch_ms`: Millisecond UNIX timestamps.

- **`TranslationReviewEntry`**:
  - `id`: Unique stable identifier (`re-<uuid>`).
  - `source_cue_id`, `target_cue_id`: Mapped cue IDs.
  - `source_text`, `target_text`: Bilingual subtitle texts.
  - `source_start_us`, `source_end_us`: Microsecond source cue timing.
  - `target_start_us`, `target_end_us`: Microsecond target cue timing.
  - `status`: `ReviewStatus` state machine enum.
  - `findings`: Array of rule-based `QualityFinding` diagnostics.
  - `approved_fingerprint`: SHA-256 fingerprint of approved target text and timestamps.
  - `approved_at_epoch_ms`: Timestamp when approved.

### 1.2 Review Status State Machine

```
              ┌───────────────┐
              │    Pending    │
              └───────┬───────┘
                      │ (Auto or User Initialized)
                      ▼
              ┌───────────────┐
              │  NeedsReview  │◄─────────────┐
              └───────┬───────┘              │
                      │ (User Marks Reviewed)│ (User Edits Text/Timing)
                      ▼                      │
              ┌───────────────┐              │
        ┌────►│   Reviewed    ├──────────────┤
        │     └───────┬───────┘              │
        │             │ (User Approves)      │
        │             ▼                      │
        │     ┌───────────────┐              │
        │     │   Approved    ├──────────────┘
        │     └───────┬───────┘
        │             │ (User Rejects)
        │             ▼
        │     ┌───────────────┐
        └─────┤   Rejected    │
              └───────────────┘
```

#### Approval Invalidation Invariant:
Any modification to an `Approved` review entry's target text or timestamps immediately resets its status to `NeedsReview` and invalidates `approved_fingerprint`. Furthermore, if an unverified modification is detected during quality evaluation, `QualityFindingCode::StaleReviewApproval` is flagged.

## 2. Stable Cue Mapping Engine

Rather than relying on naive array indexes (which break when cues are split, merged, or filtered), the review mapping engine uses stable identifiers and microsecond start bounds:

1. **Direct Translation ID Prefix**: Cues generated by STEP 22 adhere to `{source_cue_id}-tr-{target_lang}`.
2. **Identity Matching**: For manual duplicates or identical track imports, `t.id == s.id`.
3. **Microsecond Start Timestamp Alignment**: `t.start_us == s.start_us`.
4. **Unmapped Cue Fallback**: Missing target cues are assigned synthetic `{source_cue_id}-unmapped` IDs and flagged with `QualityFindingCode::UnmappedCue`.

## 3. Terminology Protection Engine

### 3.1 Protected Terms vs Preferred Terminology

- **Protected Terms**: Brand names, technical identifiers, product names, acronyms (e.g. `Open Media Workbench`, `llama.cpp`, `FFmpeg`, `Whisper`). Must be preserved verbatim without unauthorized translation or morphological mutation.
- **Preferred Terminology**: Domain-specific glossary terms where a preferred translated variant should be used.

### 3.2 Unicode & Bengali-Safe Word Boundaries

In `crates/opentake-core/src/ai/translation/review/terminology.rs`:

- Single-word terms utilize Unicode standard word boundary segmentation (`unicode_words()`), preventing false positive substring matches inside longer words (e.g., preventing `Whisper` from matching inside `AntiWhispering`).
- Multi-word terms verify alphanumeric boundaries on leading and trailing characters.
- Complex Bengali grapheme clusters (যুক্তবর্ণ) such as `বিজ্ঞান` and `প্রযুক্তি` are preserved without byte truncation or illegal splitting.

### 3.3 Placeholder Protection & Masking (`ProtectedTermMasker`)

For offline AI translation pipelines:
1. Protected terms in input cues are masked with opaque collision-resistant tokens: `__OMW_TERM_0__`, `__OMW_TERM_1__`.
2. Input texts are translated offline by the local model.
3. The translation output is unmasked. If the translation model dropped or duplicated any placeholder token, the pipeline rejects the translation and falls back with an explicit validation error, preventing corrupted subtitle rendering.

## 4. Local Translation Memory

### 4.1 Storage & Privacy

Translation memory is stored 100% locally on the user's workstation in `.local/share/opentake/review/translation_memory.json` (or OS equivalent). No data is ever transmitted to remote APIs.

### 4.2 Exact Matching with Whitespace Normalization

Source texts are normalized by:
1. Trimming leading and trailing whitespace.
2. Collapsing consecutive whitespace sequences into single spaces.
3. Lowercasing for ASCII and Unicode case equivalence.

When a reviewer navigates cues in the Bilingual Review Panel, exact matches from translation memory are retrieved instantly with usage frequency metadata and one-click application.

## 5. Quality Validation Engine

Rule-based quality diagnostics evaluate each entry for grounded, observable issues:

| Code | Severity | Description |
|------|----------|-------------|
| `MISSING_TRANSLATION` | Error | Target text is empty or missing. |
| `EMPTY_TARGET_TEXT` | Error | Target text contains only whitespace. |
| `UNMAPPED_CUE` | Error | No target cue corresponds to this source cue. |
| `PROTECTED_TERM_CHANGED` | Error | A protected brand name was altered or translated. |
| `PREFERRED_TERM_MISSING` | Warning | Recommended glossary translation was omitted. |
| `EXCESSIVE_READING_SPEED`| Warning | Target reading speed exceeds 25 characters/sec. |
| `EXCESSIVE_LINE_LENGTH` | Warning | Subtitle text exceeds standard 84-character display bounds. |
| `SOURCE_TARGET_TIMING_MISMATCH` | Warning | Target start or end timestamps differ from source. |
| `POSSIBLE_UNTRANSLATED_TEXT` | Warning | Target text is identical to source for non-proper nouns. |
| `STALE_REVIEW_APPROVAL` | Error | Entry is marked Approved but revision fingerprint does not match content. |

---

## 6. Persistence & Project Embedding

Review documents are serialized and embedded directly within the canonical `SubtitleDocument.metadata` under the key `"translationReview"`. When projects are saved as `.omwsub` files, the full review state, approval fingerprints, and glossary references persist without modifying the underlying source-language subtitle tracks. Legacy `.omwsub` projects without review metadata load gracefully without errors.
